## 最初开发需求

用户希望有一条按照现实时间向下排列的个人时间轴。记录不要求用户先选择起止时间，而是用自然语言表达，由 AI 判断：

- “刚才看了 15 分钟书”：从当前时间向前回溯 15 分钟，记录为已完成的读书时段。
- “吃完饭了”：把现在作为结束时间，由 AI 保守估计约 10 至 15 分钟等合理时长。
- “等下计划去做什么”或“开始做什么”：只填写开始时间，结束时间保持空白。
- “结束了”：结算此前尚未结束的事项，补上当前结束时间。

每个条目有一个类似标题的“做了什么”，还可以附一段感受、情绪或随笔。随笔必须完全保留用户原文，AI 不得编辑。应用有一个角色控制中心；每次新增日程，都把“时间 + 标题 + 随笔”卡片同步到当时所有已选角色的主聊天。

## 第一版产品决策

### 与角色日程分离

仓库原有 `DailySchedule` 描述角色一天在做什么，会影响角色自己的情绪、主动消息和小屋状态。“我的日程”描述用户现实生活，写入方向相反，因此使用独立 `MyScheduleEntry` 和 `my_schedule` store，绝不修改角色的 `DailySchedule`。

### 随笔原文保护

界面把“自然语言记录”和“随笔原文”做成两个独立输入。调用解析 API 时只发送自然语言记录、当前时间与开放事项列表，不发送随笔。随笔按输入字符串直接写入 IndexedDB、时间轴和聊天卡；结算时若补写随笔，只在旧随笔后追加换行和新原文。

### 收件角色快照

控制中心保存 `selectedCharIds`。新建条目时把当前选择复制到条目的 `recipientCharIds`，并逐个写入对应角色主聊天。之后修改控制中心不会向新选角色补发历史，也不会撤回旧角色已经收到的卡片。这样能避免一次角色选择变化意外公开过去记录。

第一版允许一个日程同步给零位角色：它仍会保存在本地时间轴，界面明确显示同步人数。

## 自然语言解析与本地校验

`requestMyScheduleCommands()` 使用 SullyOS 全局主 API，不注入角色资料、聊天记忆或 MCP。一次输入会返回按叙述顺序排列的一个或多个动作；一句话包含多件拥有独立时间语义的事时，必须拆成多个时间轴条目。每个动作仍只有三种类型：

- `create_completed`：已完成事项，包含标题、开始、结束和可选估时标记。
- `create_open`：计划或已经开始但尚未结束，只保存开始时间。
- `finish_open`：选择一条开放事项进行结算。

`resolveMyScheduleCommand()` 是最终事实边界：

- 完成事项缺少合法开始时间时，按 AI 给出的合理分钟数从结束时间回溯，缺省为 15 分钟。
- 开始必须早于结束；异常超长、未来完成时间或无法解析的时间会安全回退。
- 开放事项不虚构结束时间；状态由开始时间相对当前时间派生为“待开始”或“进行中”。
- 结束动作优先使用模型选中的条目；缺失目标时结算最近开始的开放事项；没有开放事项则报错。
- AI 只生成简短标题，不能添加感受或角色语气。

## 聊天同步

每个收件角色获得一条 `role: user`、`type: score_card` 的主聊天消息，卡片类型为 `my_schedule_card`。这表示用户主动把自己的现实安排告诉角色，不伪装成角色说的话。

条目保存 `messageIdsByCharId`。开放事项结束时：

1. 更新本地条目的 `endAt` 与可选追加随笔；
2. 用 `DB.updateMessage()` 更新原卡正文；
3. 用 `DB.updateMessageMetadata()` 更新原 `scoreCard`；
4. 不再新增第二张“结束”卡。

`normalizeMessageContent()` 会把卡片转成后续聊天、归档和记忆链路可读的文本，并要求角色不得擅自改写随笔、不得声称已经替用户完成现实事项。应用本身不会请求角色自动回复，也不直接写长期记忆；角色是在主聊天时间线中收到用户主动同步的信息。

删除本地条目不会自动删除或撤回已经同步的聊天卡，删除前 UI 会明确提醒。

## UI 与交互

- 首页主体是一条持续向下生长的现实时间尺，按 `startAt` 从早到晚排列。
- 同一天内，每分钟按 3px 映射到纵向时间尺：事项之间的空闲时段形成同比例间距，有结束时间的卡片以持续时长决定最小高度。卡片内容仍可自然撑高，所有条目保持普通文档流，因此长内容、相邻事项或时间重叠都不会互相遮挡；跨天时重新起尺，不渲染整夜空白。
- 当前时间使用横穿页面的珊瑚红刻线；完成、待开始、进行中使用不同状态标记。
- 每条事项可选“学习 / 娱乐 / 休息 / 睡眠”时间标签。标签会改变整张卡片的浅色底、轴上圆点和文字标签，不能只靠颜色传递含义；旧记录和无法判断的事项保持未分类白色卡片。
- 日程色板固定为课程表式的清透粉彩：天蓝 `#DDEBFA / #6E9FD8 / #264E78`、玫粉 `#F9DFE8 / #E3789B / #713247`、薰衣草紫 `#E9E4F7 / #A18FD3 / #4D416F`、薄荷绿 `#DDF3ED / #64C5B0 / #285F55`、琥珀黄 `#F8E8CA / #DBA653 / #6F4D24`，每组依次为底色 / 强调色 / 正文字色。当前学习、娱乐、休息、睡眠分别使用天蓝、玫粉、薄荷绿、薰衣草紫；琥珀黄继续留给后续标签。
- 有完整起止点的卡片在时间范围后直接显示结构化持续时长，例如 `01:20 — 01:57 · 37min`；跨小时显示为 `1h 5min`。大标题与时间轴之间以一条紧凑汇总带显示当前记录日四类标签的累计时长，进行中事项累计到当前时刻，未来计划记为零。
- “当前记录日”不是自然日：零点不会自动切换。用户录入跨夜睡眠后主动点击“进入下一天”，系统才把当前未归档条目 ID 和归档时刻组成一份 archive，并从当前页移入历史列表。
- 历史归档按归档时间倒序列出，可逐份打开只读时间轴；不显示“现在”刻线，也不提供编辑/删除入口。归档时仍开放的事项保留原始未结束状态，但累计只计算到 `archivedAt`，不会随现实时间继续增加。
- 每张卡片提供编辑入口。标题、开始时间、是否已有结束时间、结束时间、估算标记和随笔都可直接修改；开始/结束时间是时间轴的结构化变量，保存后会立即影响排序、间距和卡片长度，而不是只修改自然语言文本。
- 时间轴日期标题旁提供“手动添加”入口。用户明确知道时间时可直接填写与编辑卡片相同的标题、开始时间、结束状态/时间、估算标记和随笔；这条路径不调用 AI，保存后立即按结构化时间进入时间轴，并同步给控制中心当时选中的角色。
- 编辑时间默认表示用户已经给出更准确的信息，因此会清除“时间为估算”；用户仍可在编辑页重新勾选。编辑已同步条目时，原角色聊天卡会原地更新，不补发新卡。
- 底部固定纵向录入区：上方填写自然语言日程，下方始终显示较大的“我的随笔”输入框，并明确“可选 · AI 不会编辑”；提交按钮位于两项内容之后。
- 右上角齿轮进入角色控制中心，逐个选择未来日程收件人。
- 视觉使用冷白纸面、深蓝文字与按钮、珊瑚红当前时刻，避免和原“时光契约”三套主题混淆。

## 数据与备份

- `MyScheduleEntry`：自然语言原文、标题、随笔原文、起止时间、估时标记、可选时间标签、收件角色快照、聊天消息 ID 映射和创建/更新时间。
- `MyScheduleArchive`：一批条目 ID、批次起止范围与人工归档时刻。归档只分组，不复制或修改条目，不触碰已同步聊天卡。
- `MyScheduleSettings`：控制中心所选角色 ID。
- `FullBackupData.myScheduleRecords`：完整导出和恢复条目及设置。
- 删除条目使用 `DB.deleteMyScheduleEntry()`；设置单例 `id='settings'` 不可通过该接口误删。

## 后续 Debug 记录模板

### 2026-08-13 · 可编辑比例时间轴

- 需求澄清：核心不是“明确 15 分钟被错误标成估算”，而是 AI 对模糊描述的估时可能与事实相差很大，所以最终卡片必须允许用户手动编辑。明确持续时长的判定仅作为额外边界保护。
- 布局：同日使用每分钟 3px 的时间比例；卡片最小内容高度为 132px，最终高度取内容需要与持续时长比例中的较大值。前一事项结束到下一事项开始之间按同比例留白；时间重叠时留白为零；跨天重新起尺。所有卡片处于普通文档流，保证不重叠。
- 编辑：新增结构化编辑页，可改标题、开始时间、结束状态/时间、估算标记和随笔。修改后的 `startAt` / `endAt` 直接参与排序和布局；校验标题非空、时间有效、结束晚于开始且跨度不超过一年。
- 聊天同步：编辑保存后复用条目的 `messageIdsByCharId`，原地更新所有已同步角色的消息正文和 `scoreCard` metadata，不创建重复消息。
- 估算边界：用户明确给出持续分钟时，即使模型没有返回绝对开始时间、本地需要按结束时间回推，也不会仅因回推被标成估算；模糊时长、默认兜底或模型明确声明的时间仍可标为估算。
