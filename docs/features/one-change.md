## 最初开发需求

“只做一个改变”是极简、local-first 的习惯实验工具。用户可以保存任意数量草稿，但正式改变必须一次只新增一个；稳定后最多获得一个增加资格。每天只记录“做了 / 没做 / 感受”，未记录不是没做，失败不清累计成功，也不使用积分、徽章、火焰、惩罚或羞辱文案。

首版完全不接 AI、API、MCP、角色、聊天或记忆。它与 `HandbookApp`、`trackers`、`tracker_entries` 没有数据或状态共享。

这个 App 之所以放进 SullyOS，而不是另做独立站点，是因为用户本来就会高频打开糯米机；桌面入口本身能形成稳定提醒。产品目的不是“提高完成率”或“给表现打分”，而是把一次只新增一个变量的长期行为实验放在每天自然会打开的位置。

### 为什么不复用手账 Tracker

上游和当前工作区都保留 `HandbookApp` 与通用 `trackers / tracker_entries`。公开上游仍把“手账”桌面入口注释掉，本工作区同样不放在桌面上。用户以后单独打开手账时，也不要把它与本功能混淆。

两者的产品语义不同：

- Tracker 是“有很多事情可以随时记录”。
- “只做一个改变”是“草稿可以很多，但正式推进数量受稳定资格、并行收缩、冻结和单任务观察期严格约束”。

因此当前实现使用独立 App、独立状态机和独立五表；以后也不要为了复用 UI 把正式进度迁回 Tracker 数据域。

## 产品语义与关键设计理由

### 三个进度概念必须分开

1. **累计成功天数 `totalSuccessDays`**：记录这个改变历史上正式“做了”多少天，只增不减。一次“没做”不能抹掉已经发生的 45 天；恢复后下一次正式成功应从第 46 天继续。
2. **当前稳定进度 `currentStreak/currentStable`**：回答“现在是否稳定”。正式 `not_done` 会把当前连续进度清零；如果历史上已经稳定过，用 `everStable` 保留“曾稳定”，UI 表达为“重新稳定”，而不是把整个历史归零。
3. **单任务观察期 `focusObservation`**：发生并行收缩后，对唯一保留任务重新进行一轮完整观察。它是重新获得扩张资格的门槛，不等于改变本身的历史累计，也不等于第一次稳定资格。

这个拆分是为了同时满足两件事：失败应真实影响“当前是否稳定”，但不能改写过去已经完成过的事实。

### 冻结的含义

冻结不是失败，也不是未记录，而是“暂时不参与正式实验”。

冻结任务仍然可以每天自由记录“做了 / 没做 / 感受”，但这些记录只是观察：

- 不增加累计成功；
- 不推进稳定进度；
- 不清空稳定进度；
- 不触发收缩；
- 不推进单任务观察；
- 不产生增加资格。

因此冻结任务可以继续存在于日常视野中，用户也可以顺手做，但系统暂时不把它当正式变量。

### 记录可修改边界

- 历史上任何**未记录**的正式日期都允许无限期补记。
- 一旦正式提交 `done / not_done`，完成结果锁定，不允许后来改成另一种结果。
- `feeling` 不参与状态机，允许以后补充或编辑。
- 晚到补记如果现在才确认过去某日存在并行中断，则**现在**触发待收缩；不穿越时间回滚或重放后续状态历史。

### 稳定周期与标准

- 全局默认稳定周期只作为**新建时默认值**。改变创建/开始时把当时数值快照进自身；以后全局默认从 30 改为 45，不会把旧改变的 18/30 动态改成 18/45。
- 每个改变可以单独覆盖稳定周期。
- 改变由“名称 + 标准 + 简介”组成。简介是可折叠自由文本，程序不分析，可写动机、好处、降低难度的方法或提醒。
- 正式改变修改标准时，旧标准继续适用于当天，新版本从下一本地自然日生效，并保留版本历史。

### 预制改变

“锻炼”和“每日随机行善”都只是普通预制模板，属于同一类改变；后者不是特殊支线，也没有额外规则。预制只负责帮用户快速填表。

## 初版实现

### 用户流程

1. 首次进入可从空白表单、锻炼预制或每日随机行善预制创建第一个正式改变。
2. 正式完成连续达到本改变的稳定周期后，获得至多一个增加资格；资格可用于开始一个草稿或恢复一个冻结改变。
3. 多个正式改变在同一自然日全部有结果且至少一个“没做”时，产生待收缩；用户选择保留一个，其它改变冻结并开始独立单任务观察期。
4. 冻结改变仍可记录，但只作为观察，不影响正式累计、稳定、收缩或资格。
5. 单任务观察连续达到保留改变自己的稳定周期后，再获得一个增加资格。
6. 正式改变只能归档，历史永久保留；未正式开始的草稿可以删除和排序。
7. 如果当前已经没有任何进行中改变，基础名额立即释放：可以直接开始一个草稿或恢复一个冻结项，不需要先拥有 `expansionCredit`。只有已经存在进行中改变时，并行新增/恢复才消耗资格。

### 核心状态机

- `totalSuccessDays`：只随正式 `done` 增加，永不因 `not_done` 或冻结清零。
- `currentStreak/currentStable/everStable`：正式 `not_done` 只清当前稳定进度；已稳定历史由 `everStable` 保留，UI 显示“重新稳定”。
- `expansionCredit`：系统级 `0 | 1`，首次稳定或观察完成时设为 1，使用后归零，不累积。
- `focusObservation`：收缩后独立于改变稳定进度保存 `changeId/targetDays/streak`。
- `pendingContraction`：保存事实日、当时正式参与者快照和实际触发时间；只有该参与集合全部有正式结果后才出现。

### 日期、标准版本与晚到补记

- 所有事实日期都使用设备本地 `YYYY-MM-DD`，复用 `utils/localDate.ts`，不使用 UTC 截断。
- 每个改变创建时快照稳定周期；修改全局默认只影响以后创建的改变。
- `one_change_standard_versions` 保存标准版本。正式改变修改标准时，新版本从下一本地自然日生效；日记录保存实际使用的 `standardVersionId`。
- 生命周期事件同时保存 `effectiveDate` 与 `effectiveAt`。冻结/归档在决定当天之后退出历史正式集合，因此该日已经完成的正式事实不会被状态覆盖。
- 历史补记只在提交当下更新当前状态；如果它补齐了过去某日的并行集合，会现在产生待收缩。系统不从第一天重放、不删除后续记录，也不回滚后续已经发生的状态事件。

### 隐私与写回

全部数据只保存在 SullyOS 主 IndexedDB。App 不读取任何角色资料，不调用模型，不产生聊天卡，也不写任何角色记忆或统一时间线。

### 数据、备份与恢复

“只做一个改变”的 schema 在 IndexedDB **v88** 引入五张独立表；截至 2026-10-05 归档复核，仓库全局 `DB_VERSION = 94`。v88 只是这五张表的历史迁移点，后续功能仍可能继续抬升全局版本；五表名称和语义保持不变：

- `one_change_changes`：改变、状态及正式进度快照。
- `one_change_records`：每日结果、感受、标准版本与记录模式；主键 `${changeId}:${date}` 防重复提交，索引 `changeId`、`date`。
- `one_change_standard_versions`：标准版本，索引 `changeId`。
- `one_change_state_events`：生命周期、收缩、观察和资格事件，索引 `changeId`、`effectiveDate`。
- `one_change_settings`：全局默认周期、资格、待收缩和观察期单例。

每个业务操作先读取最新快照，再通过一个跨五表 `readwrite` 事务整体提交；模块内队列避免双击导致并发覆盖。五表均进入 `FullBackupData`、普通完整导入导出及 OSContext v2 全量/纯文字分片备份。

当前数据库回归测试固定以真实 v87 老库为历史起点，升级结果必须与代码中的 `DB_VERSION` 保持一致，并检查五表及关键索引仍存在、旧数据保留；不要把升级后的全局版本写死为数字。

### 入口与界面

桌面名“只做一个改变”，Phosphor `Target` 图标，独立 `AppID.OneChange`，接入 PhoneShell 懒加载、点击预热、空闲预热和自理安全区。

当前 UI 仍以单个 `apps/OneChangeApp.tsx` 为主编排，业务状态机放在纯 TypeScript `utils/oneChange/engine.ts`，存储通过 `utils/oneChange/repository.ts` 与 `utils/db.ts` 处理；不要把状态机重新散回 JSX handler。

## 设计源与 Ardot 协作

首版 UI 是在 WorkBuddy 中生成并落到可编辑 **Ardot** 画布，不是只有 PDF 截图。

- Ardot 文件 ID：`718653974368521`
- 文件地址：`https://ardot.tencent.com/file/718653974368521?from=workbuddy&node_id=0%3A1`
- 当前已验证 Ardot 云端 MCP 可以直接读取该文件的结构化节点；配置名可用 `ardot-remote`，远程入口为 `https://ardot.tencent.com/mcp`。
- 2026-09-30 的只读连通性测试成功识别该文件、`Page 1`、24 个顶层节点，以及 S1/S2/S4…S13 等界面。

历史现场还验证过一类 Codex 侧连接故障：`ardot-remote` 的用户级配置若误写成空的 stdio 服务（例如 `type="stdio"` 且 `command=""`），即使条目存在也不会建立 HTTP 连接。当时通过 `codex mcp remove ardot-remote` 后重新执行 `codex mcp add ardot-remote --url https://ardot.tencent.com/mcp` 恢复，并用 `codex mcp get ardot-remote` / `codex mcp list` 确认 transport 为 `streamable_http`。这是历史 Codex 环境中的已验证修复配方，不把 OAuth 自动完成、配置文件位置或具体字段布局外推成所有后续客户端版本的固定机制；一次性交接码也不要当成可续期凭据，连接失效时应在**实际承担本次调用的 Agent 客户端**重新建立授权，不要复制旧码。

以后调整 UI 时，优先让支持 MCP 的代码 Agent 读取 Ardot 原始节点、布局、字体、颜色、圆角、间距和组件层级，再映射到 SullyOS React/CSS；结构化节点返回过大而被截断时，按子节点 ID 分批读取，不要强求一次拉完整画布。PDF/截图只作为视觉核对和兜底，不要重新靠看图猜尺寸。

**隐私边界**：Ardot 的截图/导出类能力可能把未公开设计上传到仓库外的 CDN，并生成带签名与有效期的公网外链；这类 URL 还可能进入开发日志，使日志本身成为敏感载体。默认只做结构化节点的只读核对；需要截图或导出时必须取得当前任务的明确授权，并且不得把签名 URL、交接码或其它临时凭据复制进项目文档、提交或长期知识。历史上曾用“生成外链后再下载到本机”的方式做视觉核对，但当前边界已收紧，因此不把该绕行配方保留为推荐操作。
