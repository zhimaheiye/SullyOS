# 聊天时间连续性与 Temporal V2 实验

> 本文记录的是**产品语义、已验证的当前实现差异、实验分支留下的可复用设计，以及真实模型验收边界**。它不是聊天纪要，也不能把实验分支误写成当前正式实现。
>
> 归档核验时间：2026-09-29。事实源为本仓库当时的实现。

- `docs/character-timezone.md` 继续负责“角色活在哪个时区”的实现约定；本文负责“历史消息发生在什么时候、旧状态是否还能当作现在、一次生成在时间线上意味着什么”。

SullyOS 的产品原则是“每个角色只有一份身份与语义时间线”（见 `PRODUCT.md`）。聊天时间连续性属于这条原则的一部分：角色不只要看到时间戳，还要正确区分**历史事实**与**当前状态**。

## 2. master 当前 Legacy 行为

下面是归档时 master 代码可以直接验证的现状，不是期望中的最终语义。

### 2.1 基础时间块仍受 `timeAwarenessEnabled` 总闸控制

`utils/context.ts` 的 `ContextBuilder.buildTimeAwarenessBlock()` 在：

```ts
if (char.timeAwarenessEnabled === false || timeOptions?.skipTimeAwareness) return '';
```

处直接返回。

因此当前 master 中，角色关闭「聊天 · 时间感知强化」时，并不只是少一条“多久没聊”的强化信息，而是连核心当前时间块都会一起消失。角色设置页目前仍写着：

> 开启后角色会记得你们多久没聊、主动贴近真实时间；关掉后这种感觉会变弱。

这与未来想要的“基础时间事实始终存在、开关只控制额外强化”并不一致。

### 2.2 普通私聊仍把 `conversational: true` 固定传入

`utils/chatPrompts.ts` 当前普通私聊构造 `buildVolatileCoreState()` 时无条件传：

```ts
timeOptions: { skipTimeAwareness: forFirePack || timelyByWorker, conversational: true }
```

Legacy 时间 framing 因而倾向把本轮理解成“用户此刻正在和角色说话”。

这对刚发完消息立即手动点生成的高频聊天没有问题，但对“用户昨天留下消息、今天才点生成”或“最后一条已经是 assistant、用户没再说话却点一次生成”的语义不够精确。

### 2.3 历史消息有绝对时间戳，但 gap 提示不是“最后发言 → 现在”

`ChatPrompts.buildMessageHistory()` 会给历史消息保留完整时间戳；Legacy 的 `getTimeGapHint()` 仍是用历史中相邻真实消息之间的时间差构造提示。

也就是说，普通私聊当前并不会稳定把：

> 距离最后一次真实用户发言到本轮生成已经过去多久

作为一条直接、客观的事实交给模型。

### 2.4 主动消息 1.0 已有“用户现在没有说话”的产品语义，但实现仍是 hidden fake-user

`context/OSContext.tsx` 当前会：

- 排除 `metadata.proactiveHint` 后寻找最后真实 user；
- 用当前时刻计算 `timeSinceUser`；
- 保存一条 `role: 'user'`、`metadata: { proactiveHint: true, hidden: true }` 的内部提示；
- 明确告诉模型“用户并没有在跟你说话，是角色想主动找用户”。

Legacy 文案还会在较长间隔时建议想念、好奇、抱怨等情绪。这个 fake-user 架构是已知技术债，但 Temporal V2 讨论中明确选择**不要把它与时间语义改造绑在一起重构**。

### 2.5 AMSG2 的 fire-time slot 架构是应该保留的正确部分

`utils/activeMsgClient.ts` / `utils/amsgFirePack.ts` 当前已经把真正易变的时间留成 `AMSG_SLOT_*`，由 worker 在实际 fire 时刻填入。未来继续改时间语义时，应保留“**实际触发时再算当前时间**”这一架构，不要退回客户端打包时冻结当前时间。

## 3. 长期产品语义：未来实现必须守住的边界

下面这些是本轮多轮讨论后已经明确的产品决策。它们不等于 master 已实现，但以后重做时间系统时不应重新猜。

### 3.1 基础时间事实与“时间强化”分开

理想语义下，无论 `timeAwarenessEnabled` 是否开启，普通聊天都应有：

- 当前真实日期 / 时间；
- 角色时区；
- 每条历史消息自己的发送时间；
- 相对时间表达的解释基准。

`timeAwarenessEnabled` 更适合作为**额外时间流逝提示**的增强开关，而不是“角色是否知道今天几号”的总开关。

### 3.2 相对时间词锚定在消息自己的发送时间

历史消息里的：

- 今天 / 昨天 / 明天；
- 今晚 / 明早 / 昨晚；
- 刚才 / 待会 / 稍后；

都必须以**该条消息自己的 timestamp** 为参照，再与本轮真实当前时间比较。

例如用户昨天说“我明天去做 X”，今天生成时，“明天”指今天；但“日期已经到了”**不等于计划已经完成**。没有后续证据时应保持不确定，而不是擅自把计划改写成既成事实。

### 3.3 手动点“生成 / 收消息”不是时间因果证据

SullyOS 的普通私聊即使高频连续聊天，也可能每一轮都需要用户手动触发生成。

因此：

- 手动点击不代表角色“刚刚才看到”；
- 不代表角色故意拖延；
- 不代表这是一条“延迟回复”；
- 也不能单凭按钮行为判断用户刚刚还在线。

系统只应提供消息发送时间与本轮生成时间；“为什么现在才回复”如果需要解释，应由角色结合上下文自行决定。

`readByCharacterAt` 是撤回 / 已读相关功能的技术状态，不应被提升为 Temporal 系统的“角色第一次看到消息”或延迟因果事实。

### 3.4 最后一个 assistant 之后的多条真实 user，要按一批 pending 输入处理

用户可以连续发多个气泡，再手动生成一次回复。

因此最后一条真实 assistant 之后的所有**真实 user 消息**都应视为本轮尚未得到回复的一批输入，并分别保留自己的 timestamp。

`proactiveHint`、hidden 系统伪输入等不能混进“真实 user”判断。

### 3.5 没有新 user 消息时，要明确是角色再次发言

如果最后一条真实可见消息已经是 assistant，而用户没有再发新消息，本轮生成应告诉模型：

- 用户当前没有发送新消息；
- 这是角色在当前时刻再次发言的机会；
- 可以延续旧话题，也可以自然开启新话题；
- 不要假设用户此刻正在进行旧话题里的动作。

这不是必须写成“主动消息通知”，只是修正普通 chat-completions 消息序列无法表达的产品层事实。

### 3.6 不给时间间隔贴固定等级标签

未来时间层不要再把间隔分类成：

- 短暂停顿；
- 离开一会儿；
- 很久没联系；
- 用户消失了。

也不要新增 10 分钟 / 30 分钟 / 1 小时之类的产品阈值来决定“现在算不算延迟”。

如果模型确实需要 gap，优先给**中性客观时长**：

> 距离用户最后一次真实发言约 23 小时。

不要让时间层替角色做关系判断。

### 3.7 时间层不规定情绪

时间语义本身不应写：

- 应该想念；
- 应该生气；
- 应该担心；
- 可以抱怨。

这些属于角色人格、关系、话题与上下文，不属于时间模块。

### 3.8 历史状态不默认持续到现在

这是这次真实使用中最重要的新结论：

> 历史消息描述的是**发送时刻**的用户状态，不是当前状态快照。

如果用户昨晚说“我再写一会儿就睡”“我现在很困”“我正在吃东西”，今天角色再次发言时，不能因为这句话仍在上下文尾部，就默认用户现在还在写、还没睡、仍然困或仍在吃。

除非用户后来重新确认，过去正在进行的行为、情绪或即时状态在经过明显时间流逝后应视为**当前未知**。

这不是要求系统推断“用户现在一定恢复了 / 一定睡过了”，而是要求模型停止把旧状态冻结到现在。

## 4. Temporal V2 实验分支留下的实现

下面内容属于 `feat/temporal-awareness-v2` 的**历史已提交实现**，不是 master 当前功能。

### 4.1 独立 temporal helper

实验分支新增 `utils/temporalContext.ts`，把时间语义从零散 prompt 中抽成纯函数：

- `isRealUserMessage()`：排除 hidden / `proactiveHint`；
- `resolveTemporalTurnState()`：识别 pending user batch 与最后真实 user；
- `formatNeutralElapsedTime()`：只格式化客观分钟 / 小时 / 天，不分“短 / 长”；
- `buildTemporalV2Instruction()`：统一生成 conversation / proactive 的 Temporal V2 instruction。

一轮请求由调用入口冻结一个 `nowMs`，再显式向下传，避免同一请求不同模块各自读 `Date.now()`。

### 4.2 V2 的核心提示约束

实验分支最终版本明确要求：

- 历史相对时间词按消息自身时间解释；
- 比较完整日期，不能只看时分；
- 不把旧消息里的行为说成用户现在仍在做；
- 没有本轮采集时间的旧“现在 / 正在 / 刚刚”只代表当时；
- 到了计划日期不等于计划已完成；
- 历史即时状态未经重新确认，不默认持续到当前。

如果当前是普通私聊且有 pending user，提示会强调“尚未得到回复”只描述消息结构，不代表消息刚刚发送；如果没有新 user，则明确这是角色当前再次发言的机会。

### 4.3 最后一轮最小补丁：conversation 也拿到客观 elapsed time

真实 A/B 调查暴露了一个缺口：V2 初版虽然已经有 timestamp、当前时间和“旧状态不能直接延续”的否定规则，但普通 `conversation` 仍让模型自己在长 prompt 中心算“昨天 04:10 → 今天 03:50 到底隔了多久”；预计算 elapsed time 只在 proactive 路径使用。

实验分支最后一轮把 neutral elapsed 注入移到 conversation / proactive 共用位置：

> 距离用户最后一次真实发言约 X。这只是客观时长，不代表用户消失、角色应当想念、抱怨、生气或担心。

并同时补上“历史状态不默认持续”的短规则。

这份最终实现目前仍存在于远端实验分支的 `utils/temporalContext.ts`。

### 4.4 指令位置也是语义契约：必须贴近生成点

Temporal V2 的时间指令不能只做到“已经拼进 prompt”。历史实验发现，在约 5.4 万 token 的长请求里，如果时间规则放在 volatile state 前部，后续实时世界、记忆、情绪等业务块仍可能覆盖其 recency，让模型重新把前夜“熬夜写文”等旧状态当成现在。

因此实验分支最终把 Temporal V2 instruction 放入 `recencyTail`：位于各业务模式块之后、模型真正开口之前。恢复这套设计时，应把“**时间连续性指令置尾、贴近生成点**”视为与指令文本本身同级的不变量，而不是可随意调整的 prompt 排版。

pending 文案也必须保持中性：“尚未得到回复”只描述最后一条 assistant 之后仍有真实 user 输入这一**对话结构**，不表示这些消息刚刚发送，也不制造“角色刚看到 / 故意晚回”的时间因果。

历史落地坐标是实验分支 Phase 1 的 `18fa4064` → `624c622b`，以及后续修复 `86e74c7b`。这些提交用于追溯设计演进，**不改变本文第 1 节的恢复原则**：旧 `feat/temporal-awareness-v2` 分支不得整体 merge 回 master，恢复时仍应从最新 master 重新移植仍有价值的小块实现。

### 4.4 DevDebug A/B 是临时迁移工具，不是长期产品开关

实验分支把 `temporalV2` 放进现有 DevDebug：

- OFF：完整走 Legacy；
- ON：普通私聊、主动消息 1.0、AMSG2 使用 V2 语义；
- 默认 false；
- 只影响 prompt / fire pack，不修改聊天历史数据。

设计目标一直是：真实模型验收稳定后，让 V2（或其后继实现）成为唯一正式逻辑，再删除 Legacy 分支与临时 A/B 开关，而不是永久维护两套时间系统。

### 4.5 AMSG2 保持 fire-time 计算

实验分支没有推翻 AMSG2 slot 架构；`temporalV2` 会随 fire pack 上传，worker 不读取浏览器 DevDebug localStorage。

V2 下“基础当前时间”与 `timeAwarenessEnabled` 解耦，而“距离最后真实 user 多久”继续作为增强信息。实际当前时间仍由 worker 到 fire 时刻填入。

## 5. 真实 A/B 调查得到的结论

这一节包含**历史对话现场 / 浏览器实验**，不能冒充 master 当前验收结果。

### 5.1 已确认不是“时间戳根本没传进去”

在真实长期聊天存档上，曾对同一上下文用 DevDebug + reroll 捕获 Temporal V2 ON / OFF 的完整 API payload。

可以确认：

- 历史消息确实带完整 `[YYYY-MM-DD HH:mm]`；
- V2 当前时间与相对时间规则确实进入最终请求；
- ON / OFF prompt 差异符合代码设计。

因此当模型仍把“昨晚做的事”当成“现在还在做”，问题不应简单归因成“旧消息没有 timestamp”或“Temporal prompt 没有进入请求”。

### 5.2 只告诉模型“看时间戳”仍然不够稳定

真实使用中出现过：

- 跨日后仍沿用上一晚的活动语境；
- 已有完整日期与当前时间时，模型仍可能自然语言上滑回“明天 / 明早”；
- 当前钟点被强调了，但被错误投射成“用户现在还在继续昨天的事”，而不是角色自己当前所处的时刻。

这说明时间连续性至少包含两层：

1. **Temporal Position**：这句话什么时候说的、相对时间词指向哪天；
2. **Temporal Persistence**：那条历史消息里描述的状态，现在还能不能继续当作当前事实。

第一版 V2 主要强化了 Position；后续真实使用暴露的核心痛点更接近 Persistence。

### 5.3 最后一轮补丁之后尚无真实模型验收结论

最后的 “conversation neutral elapsed + 历史状态不默认持续” 补丁已经提交在实验分支，并有确定性测试覆盖。

但本次归档的对话里**没有留下补丁后的真实模型 A/B 验收结果**。

因此当前只能写：

- 代码层实现存在；
- prompt 构造的确定性测试存在；
- 补丁前的真实 A/B 已证明问题与信息链路；
- **补丁后是否达到实际聊天体验目标仍未验证。**

不要把它写成“已修复”。

### 5.4 2026-10-14 · 再次出现跨日沿用旧话题

用户提供的 DevDebug 导出中，最终聊天回复生成于 **2026-10-14 13:59:20 UTC**（北京时间 **21:59:20**），模型仍把用户确认发生在前一天的 Discord 接口测试称为“今天”的事，同时说“快十点”。后者与北京时间钟点相符；问题是把旧事件归入当前自然日，不能把这两种时间判断混为一谈。

这份导出的三次模型请求将 `messages` 整组折叠，无法核对最后一条真实用户消息的时间、历史时间戳、角色时区、`timeAwarenessEnabled` 状态、实际注入的当前时间块或 MCP 工具结果。因此它记录了**用户报告的跨日语义问题及最终台词**，尚不能单靠这份日志证明是哪一段提示失效。当前代码仍固定给普通私聊传 `conversational: true`，间隔提示也只比较历史相邻消息；这些是与现象相关的已确认 Legacy 缺口，但不是本次单例的完整因果证明。`fd0c6e81` 近期只改了间隔文案，并未补齐这两项判定。

恢复 V2 时可把此例加入第 7 节的跨自然日验收：保留当前日期与用户消息原始日期，核对模型是否能把“昨天完成的事”归到昨天。复现前先开启 DevDebug「记录完整内容」才能检查最终 `messages`；仅提取必要的时间字段和提示片段做对照，完整私人聊天不入库。旧实验分支仍应按第 6 节选择性移植，而非整体合并。

2. 重新阅读：

   - `docs/handoff/CURRENT.md`

3. 把本文第 3 节当作产品契约；只从旧分支移植仍适合当前架构的小块实现。
4. 优先恢复“当前时间 + 历史 timestamp + pending/no-new-user + neutral elapsed + state persistence”这一最小闭环。

8. 只有真实模型稳定后，才讨论正式替代 Legacy。

## 7. 验收场景

恢复开发时至少覆盖这些真实语义，而不是只测字符串是否存在：

- **高频连续聊天**：用户刚发完就手动生成，不应被标成“延迟回复”。
- **跨自然日**：昨天消息里的“明天”今天应指今天；但不自动断言计划完成。
- **历史即时状态衰减**：昨晚“我再写一会儿就睡”不能在今天默认成“你现在还在写”。
- **旧表情包**：昨天最后发的表情包今天不应被模型当成刚刚发出的即时反应。
- **多个 pending user 气泡**：最后 assistant 后的真实 user 全部属于本轮输入，各按自己的 timestamp 理解。
- **无新 user 的再次生成**：角色知道用户现在没说新话，可以自然再次发言，但不能假定用户在线、醒着或正在做旧事。
- **reroll**：历史消息 timestamp 不变；“当前生成时间”使用 reroll 当下，而不是第一次回复的旧时刻。
- **主动消息 1.0**：last real user 排除 `proactiveHint`，时间事实保持中性。
- **AMSG2**：当前时间必须取真实 fire 时刻，不能取客户端早先 pack 时刻。
- **时间强化关闭**：未来若正式采用本文契约，基础当前时间仍存在，只省略额外 elapsed 强化。
- **情绪边界**：时间层不自动规定想念、生气、担心或抱怨。

自动测试只应验证 prompt / turn-state / timestamp 构造等确定性事实。真实模型是否按语义行动，必须另做实际 API / 浏览器验收；“测试通过”不能替代真实聊天体验。

## 8. 已明确不在本任务内的事情

- 不顺手重构主动消息 1.0 的 hidden fake-user。
- 不把撤回的 `readByCharacterAt` 改造成时间因果系统。
- 不给用户状态建立复杂“心理 / 生理半衰期模型”。
- 不新增固定的 gap 分类阈值。
- 不永久维护 Legacy / V2 双实现。
- 不因为模型偶发不服从，就先扩大成整套世界状态引擎。

先解决最基础的时间连续性：**知道过去是什么时候，也知道过去不等于现在。**
